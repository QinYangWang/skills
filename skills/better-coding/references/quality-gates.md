# Quality gates

Run these in order. A later gate does not excuse a missing earlier one. The
point is not ceremony; each gate catches a different way an agent-written change
looks finished while it is not.

## Gate 0 — Scope and reproduction

**Passes when**

- the affected subsystem and runtime path are named;
- the reporter's exact case is reproduced, or a failing test exists;
- the sibling/caller/state map is written;
- the goal and non-goals are one paragraph each;
- the change kind and its base branch are named, and they agree.

**Does not count**

- "I can see the bug in the code."
- A screenshot without the reporter's platform/config.
- A test that asserts the current (buggy) behavior.
- A branch that carries two change kinds, one of which is a new surface.

**Record:** the reproduction command and its output.

## Gate 0b — Agent-facing context budget

If the repo has an `AGENTS.md`, repo skills, MCP tools or other text the model
loads up front, measure it.

**Passes when**

- the exact text the model sees is generated by code, not hand-copied;
- its byte count is committed in one budget file;
- a test asserts the committed budget equals the measured text;
- CI fails when a value grows above main, unless the owner adds the agreed
  approval label;
- the owner can say why the current size is worth its cost.

**Does not count**

- a line count as a proxy for token cost;
- editing the budget file without re-measuring;
- growth hidden inside a feature PR;
- a budget no test reads.

**Record:** the budget file, the measuring test, the CI comparison, and any
approved growth. See the context-budget deliverable in `converge.md`.

## Gate 0c — Branch and contribution fit

Before the diff is read, the tree has to be the one that ships.

**Passes when**

- the base branch matches the change kind: fix → stable line, new surface → next
  minor, breaking change → major line, chore/docs/tests → stable line;
- the branch carries one kind, and the subject of the header says which;
- new user-visible surface names an approved design note, and the note says who
  is affected and what it costs;
- a refactor names a measured reason and is not mixed into a fix;
- no reformat, repo-wide rename or drive-by cleanup is in the diff.

**Does not count**

- "It was easier to open it against main."
- A feature released in a patch version.
- A note written after the implementation, describing the API that came out.
- A refactor explained only as "cleaner" or "more readable".
- A large diff whose formatting noise hides the behavior change.

**Record:** the base branch, the change kind, the design note link or why none
is needed, and the cost measurement for a refactor. See
`contribution-and-branches.md`.

## Gate 1 — Red check

Put the old code back (or check out the base) and run the new test. It must fail
with a real failure that names the behavior:

```
--- FAIL: TestCorruptIndexKeepsLastGood (0.00s)
    cache_test.go:88: got 0 entries after corrupt read, want 12000
```

**Passes when**

- the test fails on the old code with a message a reader can understand;
- the test passes on the new code;
- the failure is behavioral, not a compile error, a missing fixture or a skip.

**Does not count**

- A test that passes on both versions.
- A test that fails because it imports a new symbol.
- A test that is skipped unless an environment variable is set.
- A test that asserts an implementation detail the fix happens to change.

**Record:** test name, old-code output, new-code result.

## Gate 2 — Break check

Break the change on purpose, in two or three different ways, and watch the new
test catch each break. The breaks should be plausible mistakes, not sabotage:

- return the old value on the error path;
- skip the write/flush/rename;
- read the user value after applying the default;
- remove the lock or move the state assignment after the handoff;
- change the unit (ms vs s), the key name, or the ordering.

**Passes when** every break makes at least one test red, and the failure names
the behavior.

**Does not count**

- Breaking a different function and calling it a break check.
- A test that stays green because it only checks that no error was returned.
- Rerunning the same unmodified test several times.

**Record:** each mutation and the test/output it produced.

## Gate 3 — Full suite (and where it runs)

Run the project's full suite, not the packages you think you touched. Guard
tests often live in packages a change does not touch.

The full suite is the merge gate, but it does not have to run on the agent's
machine. Split it:

- the agent iterates with a **changed-scope check**: format, lint, typecheck of
affected packages and dependents, and the tests beside the changed files;
- CI runs the **full suite** at the pushed head;
- the record names the full-suite run and the SHA, not a claim that the agent
ran everything locally.

A changed-scope check is not a substitute for the full gate. It only decides
when the agent is ready to push. If the changed-file map cannot be resolved,
the test selection must **fail open** and run everything. Security and policy
checks fail closed.

**Passes when**

- the full suite runs at the **pushed head**, not an older base;
- it finishes; a timed-out package is a failure, not a normal run;
- tests are isolated from the real machine (temp HOME/config, pinned caches,
  no live agent config);
- tests do not reach the network; a vendor is served by a local fake built from
  real bytes;
- whatever a test starts (process, goroutine, timer, server) ends when the test
  ends;
- timing tests wait for state, not a duration, and leave room on both sides;
- concurrency changes run under the race detector, with a delay injected into
  the writer where relevant.

**Does not count**

- "All tests pass except <package>" without naming the failure and filing it.
- "Fails the same on main" without fetching main and naming the SHA.
- "Passes alone."
- A run that was cancelled by the next push.
- A green rerun that hides a red first attempt.
- A full suite run at a different tree than the one pushed.
- A local changed-scope check presented as the full suite.
- A test-selection map that silently skips jobs when the diff is unresolved.
- Parallel full suites on one machine, if the project's resources cannot take
  it; that produces timeouts, not evidence.

**Record:** the command or CI run, where it ran, head SHA, pass/fail counts,
every red with its issue/owner, and what was not run.

## Gate 4 — Real use

Where the change meets a vendor, account, config format, binary or user
surface, try the real thing in a sandbox:

- a copy of the real config, not the live one;
- a copy of the credentials, not the only copy;
- the vendor's real response, not a mock you wrote from the same assumption;
- the real binary the user runs, not only a unit test;
- the reporter's platform, not a cross-compile.

Match the evidence to the change type; do not apply one template to everything:

| Change | Required evidence |
| --- | --- |
| Logic, data, state, protocol | A failing test first, then the fix. |
| Visual spacing/colour/alignment | Before/after captures; no test for a nitpick. |
| UI motion/timing | A short recording. |
| Server-only, no visible surface | The test plus a short runtime transcript. |
| Model-facing text/tools/titles | An eval or a measured context budget. |
| Release/packaging | A packaged artifact smoke against an old data snapshot. |

**Passes when** the real path works and the record names what was used.

**Does not count**

- A unit test with a fake that encodes your assumption.
- A `GOOS` build standing in for a platform test.
- "Not tried on Linux" shipped as working.
- A live gateway or a running app being touched outside a sandbox.

**Record:** account/key/config/binary, sandbox location, result. If impossible:
`Not run: <check> (<why>)` in the commit and PR.

## Gate 4b — Model-facing behavior (evals)

A unit test cannot tell you whether a model will call the right tool after a
wording change. When the change touches prompts, tool descriptions, schemas,
generated titles or other model-facing text, add an eval.

**Passes when**

- at least one case reproduces a real bad experience or guards a real good one,
  and names its source;
- the case fails on the old text and passes on the new text;
- controls prove the fix did not overcorrect;
- each case runs several times; a case fails when half or more samples fail;
- the comparison is against a baseline on the same model, not an absolute
  score;
- no user data is in cases or fixtures;
- the cost is recorded, and the full run is manual if CI cannot pay for it.

**Does not count**

- a single sample presented as stable;
- a case that only checks the prompt contains a string;
- a model upgrade without a baseline run;
- a paid eval run in CI without a budget.

**Record:** eval name, model, number of samples, baseline, pass/fail, cost.
See the evals deliverable in `converge.md`.

## Gate 5 — Cross-platform and architecture

An `int` conversion safe on arm64 can wrap on amd64. Windows reports a refused
connection differently. A path that differs by OS is tested with each OS's
value. A UI change is tried in the engines the app actually ships, not only the
test browser.

**Passes when** the change is built and tested on every platform/architecture it
claims to support, and a platform-specific report is checked on that platform.

**Does not count**

- A cross-OS build; it does not compile `_test.go` files.
- A test that only passes on the author's OS.
- A browser-engine test standing in for a native webview.

**Record:** the platforms/architectures and the command/output for each.

## Gate 6 — Contract and docs

**Passes when**

- the owning subsystem reference is updated in the same change when a
  responsibility, interface, state transition, compatibility rule or failure
  behavior changes;
- every link resolves and every cited symbol exists;
- the semantic change is described by trigger, before, after and verification;
- the commands and route table in `AGENTS.md` still match reality;
- an internal refactor that preserves contracts says so.

**Does not count**

- A doc-only update standing in for behavior verification.
- A reference that copies implementation details and goes stale.
- A new page that duplicates an existing fact instead of linking to it.

**Record:** files updated and the contract that changed.

## Gate 7 — Record

**Passes when** the commit has a conventional header and the body has:

```
<type>(<scope>): <subject>

Ran at <pushed sha>:
- Red check: ...
- Break check: ...
- Full suite: ...
- Real use: ...
- Not run: ...
Docs: ...
```

and the PR repeats it.

**Does not count**

- "Tests pass."
- A pointer to a chat, a push note or "the CI".
- A body whose SHA is not the pushed head.
- A placeholder such as `SUITE_LINE`.
- Two commits sharing one body word for word.
- A body carrying the changelog wording, or a header carrying the evidence.

**Record:** the body itself. This is the artifact a later review reads.

## Gate 8 — Merge

**Passes when**

- the merge goes into the branch the change kind belongs to, not "whichever is
  easier";
- a reviewer pulled the head and merged it onto that branch;
- the acceptance gates were run on the result;
- the merge names the reviewed head:
  `gh pr merge --match-head-commit <reviewed sha>`;
- the PR comment says what was run, at which head, before the merge;
- a push after the review triggers a new review, not a merge — this includes a
  push by the owner, whose edit is a contribution like any other;
- a fix that ships in the next minor is cherry-picked forward with
  `git cherry-pick -x <sha>`; the stable line is never merged into the minor
  line;
- the PR is still to its goal; a known problem is fixed or filed, not merged
  past.

**Does not count**

- Reading the diff and approving.
- Merging a later push under an earlier review, or an owner edit under a review
  that ran before it.
- A draft PR merged without marking it ready.
- A known red test in the PR's own new test.
- A feature merged into the stable line, or a fix merged into the minor line.
- A merge commit that pulls the whole stable line into the minor line "to keep
  it up to date".

## Gate 9 — Release

**Passes when**

- the tag is on the line it ships from, and is an ancestor of that line's
  `origin`: a patch is tagged on the stable line, a minor is tagged on the
  stable line **after** the minor line was merged into it once — never on the
  minor line itself;
- a CI run on the tagged commit (or a later one containing it) **finished**
  green; a run cancelled by the next push is not a pass;
- the release has all expected assets;
- the release is marked latest and is the highest version;
- the version was free: `git fetch --tags` and check the commit is not already
  tagged;
- the publish step passes `make_latest`/equivalent only to the highest version;
- a plugin/package version named in a user-facing message is actually published
  (`npm view <pkg>@<version> --prefer-online` or equivalent).

For a product that ships frequently, the release train is part of the gate:

- a **disposable preview** exercises the whole pipeline (build, sign, package,
  smoke, publish) on a throwaway version that no stable install can receive;
- a **release candidate** is the only source for a stable promotion; stable
  builds the verified candidate commit, not the default branch HEAD, so merges
  during verification do not leak in;
- the **packaged artifact** is opened against a seeded old data snapshot, so a
  backend, migration or bundle that cannot start fails before publishing;
- only a plain stable version is marked latest; preview and candidate builds
  are prereleases.

See the release-candidate deliverable in `converge.md`.

**Does not count**

- A tag with no release.
- A green rerun that hides a red first attempt.
- An older release published later taking "latest".
- A known-red publish pipeline whose color hides a new package's failure.
- A release that was never opened or executed as the artifact users install.

**Record:** tag, commit, CI run id/attempt, asset count, latest marker,
`npm view` output where relevant.

## Gate 10 — Learn

If the change came back, was reverted, needed a follow-up, or was verified too
thinly, it becomes a lesson. If the same lesson is seen on three separate days,
it becomes a code standard and, where possible, a guard test. See
`lesson-loop.md`.

This gate is not optional because the change "worked". The question is whether
the next agent would make the same mistake.

## What does not count (quick reference)

| Claim | Why it fails |
| --- | --- |
| "Tests pass." | No command, no output, no head. |
| "Fails the same on main." | main was not fetched; the SHA was not named; the red was not filed. |
| "Passes alone." | The full suite is the requirement. |
| "The local fast check passed." | A changed-scope check is not the full gate. |
| "I raised the context budget." | The measuring test must pass, and growth needs the owner. |
| "The review bot approved." | A scoped review is not a merge gate. |
| "Rerun is green." | The first attempt hid the cause. |
| "It builds for Windows." | A build does not run the tests or the app. |
| "The fake returns the same shape." | The fake encodes your assumption, not the vendor. |
| "I tested it locally." | Which machine, which config, which head, which command? |
| "Not tried, but it should work." | Then it is not done and users are not told it works. |
| "The PR is approved." | Was the reviewed head the merged head? |
| "The tag is pushed." | A tag is not a release until the assets are published. |
| "I opened it against main — it was easier." | The change kind decides the base branch; a feature there has no release path. |
| "It's only a small API addition." | New surface needs an approved design note before the code. |
| "I tidied the file while I was there." | A stylistic refactor buries the fix; it goes in its own change. |
| "I fixed up the changelog entry." | The changelog is generated from conventional headers. |
| "The owner approved it, so I merged it." | An owner edit is a new head; re-run the gates at it. |

## Adapting the gates

`converge.md` fills the exact commands. A project's `scripts/verify.sh`
should run the gates that can be automated, in this order:

1. commit header convention and changelog check over the range being pushed;
2. format/lint/typecheck (fast, deterministic);
3. changed-scope tests and dependents;
4. full suite in a sandbox (or print the CI run that owns it; never fake it);
5. race/timing checks where relevant;
6. real-use check (or a printed `not run` with the reason);
7. agent-context budget, if the repo measures it;
8. a summary that names what ran and what did not.

The script must fail on the first failure and on an unfilled `TODO`. A verify
script that prints "not run" and exits 0 is worse than no script: it turns a
missing check into false evidence.

## Review agents

If the repo uses AI review, scope each agent to one concern. A good review agent
looks like a scoped test-review or UI-consistency check:

- explicit include/exclude globs; no repo-wide sweep;
- only the lines the PR changed; untouched legacy is not a finding;
- a budget per run and per PR, and a neutral conclusion;
- one fix per finding, on the smallest relevant line;
- an exact, short no-findings output (`All clear`), so an empty review is
  unambiguous;
- for tests, permission to ask for **fewer or smaller** tests, never more
  coverage;
- no inference about authorship from style, and no demands for evidence the
  change type does not require.

A review agent is not a merge gate and must not merge, change policy, or expand
its own scope. See `templates/review-agent.md`.
